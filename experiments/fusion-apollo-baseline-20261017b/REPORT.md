# Fresh baseline outcome

The benchmark executes Fusion's Apollo Federation path on source-built net10.0 assemblies from platform `43a8dca2bd479ddc411d832ed97e42d9fcc8bd85`, using benchmark `941599e4e27719084189e12d737e147069fdf794`. Every live subgraph `_service.sdl` matches the archived source schema except one terminal newline. The original TestQuery plan contains two root operations, one Apollo operation and ten Apollo batch operations. Its seven actual HTTP fetches contain eleven `_entities` selections and twenty-four entity representations. Four requests batch entity selections through GraphQL aliases. Authorization propagation is present. [Fidelity details](results/fidelity/fidelity-verification.json) retain the exact requests, plans and responses.

The two-run plain campaign completed all planned controls with zero failed scenario checks. The first original run survived an unrelated focused-driver setup failure; it was retained and never repeated. The failed script, error and bounded recovery are preserved. Native request, duration, success and iteration counts agree after setup exclusion, and summary totals include exactly those excluded setup requests. The original benchmark validates response structure once per VU, with status/error checks every iteration; focused controls compare complete captured data once per VU.

The baseline is a reference envelope, not proof of a performance improvement. Original TestQuery at zero source delay ranged from 0.5846 to 0.6045 gateway CPU ms/request, 4072 to 2936 successful requests/s and 42.08 to 46.55 ms p99.9. Across these launches, CPU/request increased 3.4% while throughput decreased 27.9%. Future candidate claims require their planned matched controls and full control envelope. Aggregate source and generator headroom does not rule out per-core, scheduling, GC or downstream limits.

The ordinary fifty-VU control is generator-limited: k6 averaged 1.907 and 1.911 of two assigned CPU cores, with one-second peaks near 1.98. Its retained 0.0789 and 0.0785 gateway CPU ms/request observations are useful scoped controls; its throughput and latency do not establish gateway capacity. A different ordinary load used in a candidate gate requires its own applicable controls. TestQuery and entities9 generator averages stayed below 1.08 of two cores.

At four-millisecond source delay, constant TestQuery measured 0.6743 and 0.6626 CPU ms/request, 1587 and 1597 requests/s, and 67.66 and 61.76 ms p99.9. The unchanged burst scenario measured 0.6626 and 0.6548 CPU ms/request, with p99.9 near 270 ms. Burst requests and tails must be compared at matching stages; individual requests and time blocks are not independent launches. The complete [table](results/analysis-table.md) and [machine-readable analysis](results/analysis.json) include per-launch results, median/p95/p99/p99.9, tail ranks and neighboring values, temporal tail clusters, CPU headroom, RSS/thread peaks and GC counter ranges.

The warmed profile campaign uses a separate launch after all plain timing. The TestQuery allocation capture records 15.120750 seconds, 61630 successful completions and 37.092032 gateway CPU seconds. One entities9 success callback crosses the trace boundary, giving 138913 callbacks inside it; the complete load has no failed checks. All three trace readers report zero lost events, and their actual bounds lie within warmed native traffic. Allocation ticks are sampled caller/type evidence and do not establish exact allocated bytes per request. Sampled thread time includes waiting threads and is not process CPU.

Counter output received SIGINT without an attached terminal and ended after a complete event with an unclosed JSON container. The raw files are preserved. Analysis closes that container in memory and uses complete events only. CPU metrics are per-second rate deltas, so the analysis sums their intervals instead of subtracting endpoints. Runtime-counter and `/proc` comparisons use matching interior callback windows; their discrepancies and timing limits are reported, not treated as phase-wide uncertainty bounds. Gateway process CPU uses ten-millisecond ticks and interpolation between hundred-millisecond observations. Fast ordinary generator startup is bracketed by its recorded launch identity because its first periodic sample follows the first request.
