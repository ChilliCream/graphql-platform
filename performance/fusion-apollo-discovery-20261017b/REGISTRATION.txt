C1: reuse Apollo representation scratch state

Caller: Apollo node -> FetchResultStore.BuildRepresentationValue -> new writer,
dedup table and JsonWriter; VariableDedupTable.Initialize sizes by all target
occurrences. Each invocation rents/clears its default table and may resize/clear
again. The original query implies at least 35,840 cleared entry bytes/request at
the minimum pool bucket sizes, despite only 24 distinct representations.

CPU evidence: BuildRepresentationValue includes 5,329.076 sampled thread-ms;
2,106.589 ms specifically follows VariableDedupTable.Resize -> RentClearedTable
-> Buffer.ZeroMemoryInternal. This is 2.9445% of filtered sampled thread time,
including 2,102.515 ms with CPU_TIME leaves. Source and allocation caller evidence
also locate the three fresh scratch objects on every warm entity fetch.

Hypothesis: retained, bounded scratch on the request's FetchResultStore removes
repeated object allocation and oversized table initialization without changing
representation JSON, deduplication or paths. Reuse must stay under the store lock,
clear only existing entries safely, reset before each lookup, and release excess
capacity on request cleanup. A smaller capacity/growth variant is within this
same hypothesis if lifetime reuse cannot preserve ownership or clearing behavior.

Risks: writer bytes escaping to pending requests, stale dedup indexes across
fetches, parallel fetch races, canceled cleanup, retained capacity after large lists,
and all-unique resizing regressions. The outgoing combined variable writer remains
independent. Native/deferred snapshot paths require regression coverage if shared.

Micro: real production FetchResultStore creation with ordinary unique counts
1/5/6/9, duplicate 96->1, mixed duplicates, unique96/1024, snapshot/null fallback,
and a large-then-small lifecycle. Setup/schema/shape compilation stays outside
timing; representation writes and affected lifecycle stay inside. Use three planned
independent timing launches, separate validated thread-scoped allocation runs,
consume results and verify JSON/path output. Abandon on meaningful ordinary or
all-unique regression, unsafe ownership, or negligible absolute saving.

C2: materialize Apollo error-attribution variables only when needed

Caller: both Apollo node forms eagerly call RepresentationValue.ToVariableValues,
but successful PendingMerge.Apply uses RepresentationValue.ResultPaths directly.
This occurs eleven times/request for TestQuery and is present on the smaller
entities9 operation. CPU attributable to ToVariableValues is only 70.663 sampled
thread-ms, so the intended claim is scoped allocation reduction.

Hypothesis: delay internal error-only conversion until exception/missing-result
handling while preserving the public ToVariableValues result contract and required
one-element outgoing variables. Predicted original saving is 1,224 bytes/request.
No generic CPU or latency claim follows from this opportunity.

Risks: transport/merge errors, missing batch results, cancellation, duplicate path
fanout, and path validity when deferred errors are emitted. Keep exception and
callback semantics unchanged. Micro the actual node/error-attribution path, not a
copied array loop. Include single/batch success and failure cases and scoped
allocation corroboration. Abandon if the necessary lifetime changes exceed this
narrow mechanism, allocation proof is unreliable, or HTTP benefit is unproven.

C3: reuse duplicate representation path-array backing

Caller: RepresentationPathAccumulator.ApplyTo allocates one new exact CompactPath[]
per duplicate-containing lookup to scatter additional paths. This is the highest
new recurring allocation caller in TestQuery: eight arrays hold 311 paths/request.
Its direct CPU is only 181.022 sampled thread-ms; the intended primary claim is
allocation reduction. EntityResultPath immutable arrays are outside this change.

Hypothesis: use pooled duplicate backing with explicit request-store ownership,
retaining it until all pending merges/errors/callbacks are finished and returning
it on Clean/Dispose. Predicted original saving is 2,680 bytes/request, offset by
any owner/tracking allocation, retention and clearing introduced by the change.
Test actual production accumulator behavior, duplicate/all-unique/mixed cases,
errors at primary/additional paths, canceled/throwing flows, concurrent nodes and
large-to-small request reuse. Prove no stale references or contract change.

Independent exclusion review confirmed this layer differs from earlier int[] path
segment pool access/retention (#10548), pool-slot arrays (#10557) and arena segment
tables (#10559). None of those policies may change. CompactPathSegment.Detach must
continue producing independent backing. Abandon on unresolved public lifetime
semantics, ownership races, worse retention, negligible net savings, or adverse HTTP.
