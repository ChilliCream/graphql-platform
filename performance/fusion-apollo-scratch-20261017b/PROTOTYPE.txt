The original warm operation builds representations 11 times: 335 target
occurrences become 24 distinct representations. Eight of these builds carry
duplicates. Its allocation and CPU profiles show per-build scratch objects and
VariableDedupTable.Resize/RentClearedTable clearing. The latter contains
2106.589 sampled thread-ms, 2.9445% of the deliberately filtered sample total,
inside a 30.0887164s trace with 114759 successful requests. Sampling is not a
call count or a promise of CPU savings. See discovery for denominator limits.

The prototype retains one table on FetchResultStore for the current request.
Normal and snapshot representation builders initialize it before each build,
using existing written-slot tracking to clear only touched entries for small
distinct sets. Temporary ChunkedArrayWriter and JsonWriter lifetimes remain
per build. TryGet receives the active writer instead of retaining it; the
native caller is updated without changing native table ownership. The store's
existing synchronization serializes construction. Payload bytes are copied to
the independent request writer before temporary buffers are returned.

Clean, subscription Reset and Dispose release the table. Idle stores retain
zero representation tables. Active capacity is still driven by the maximum
lookup occurrence count and collision growth within the request, not capped
at a fixed number; the original operation normally reaches 8KiB of table
storage. A 1024-unique lookup reaches at least 64KiB. Relative to immediate
per-fetch release, this increases live table memory during downstream waits;
matched HTTP burst/postburst memory and GC observations are required. Full
mixed-size request lifetimes, not only repeated identical lookups, are tested.

Rejected prototype cfbb8fcdf1 retained the writer, JsonWriter and table for the
request. Its first byte chunk keeps 128KiB live during downstream waits,
potentially about64MiB at500 simultaneous requests. It was rejected before
measurement, is preserved in experimental history, and is not the frozen
candidate. This narrowing remains inside the registered C1 scratch lifecycle
hypothesis.
