# Remaining response-domain evidence screen

No further candidate is registered. This screen uses the already-published warm CPU/allocation summaries from discovery commit 2c47637e385c25a3cea65d8df1d9be8b4a37871e and pinned baseline 43a8dca2bd479ddc411d832ed97e42d9fcc8bd85. It does not add profiling, runtime diagnostics or benchmark runs. Allocation ticks are sampled events, not exact counts or exact per-request allocation.

The response-domain prototypes are C7 direct incoming arena reads, C10 contiguous temporary sequence coalescing, C13 compact alias-root scratch and C15 private alias-result scratch reuse. C7/C10 passed their micro gates and await real-load validation; C13 is abandoned. C15's completed native gate does not establish a net benefit. No existing failed candidate is reopened by this screen.

The source-document table starts with an empty List and grows to capacities 4, 8 and 16. If all seven original network documents register in one composite, the conventional 64-bit allocation bound is 32 B for the list plus 56 B and 88 B backing arrays, 176 B total. Existing samples do not establish the exact registered-document count. Pre-sizing capacity eight can save only the first 56 B allocation in that case and charges smaller responses extra capacity. A cache would need to retain the index table through response disposal and clear document references before reuse, introducing another lifetime-spanning small cache variant. No exact original-query savings or useful independent mechanism is established, so it is not registered.

The apparent OperationPlanExecutor/ValueCompletion allocation callers arise from inlining. Source inspection locates the actual collection at Text/Json/CompositeResultDocument.cs: _sources, AssignSourceValue and the formatter accesses. CompositeResultDocument.Dispose currently disposes metadata; this screen does not change its ownership or deferred-response behavior.
