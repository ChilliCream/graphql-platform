Production and six new lifecycle tests implemented independently from baseline 43a8dca2bd479ddc411d832ed97e42d9fcc8bd85. Evidence: fresh warm allocation summary in discovery commit 2c47637e385c25a3cea65d8df1d9be8b4a37871e attributes 110 SourceSchemaResult[] allocation ticks (102 + 6 + 2) to SplitResponse through ExecuteAliasBatchStreamAsync. Sampling is not an exact allocation count. The observed original query has four incoming alias batches of 2, 3, 2 and 3 items. Exact-sized reference arrays imply a static 176 B/request opportunity on the existing 64-bit layout, before cache misses. This is an upper bound, not measured per-HTTP savings.

Mechanism: a single ThreadStatic SourceSchemaResult[] slot caches only arrays with at most 16 entries. Rent detaches the slot; logical itemCount remains authoritative even when capacity is larger. Return clears the whole cached capacity. Larger arrays retain their existing fresh-allocation path. Maximum retained array is 152 B per participating thread, not a global cap; thread migration can reduce reuse. The array never escapes the private client iterator; individual results keep their existing ownership.

Split/broadcast failure clears and returns partially populated scratch. An outer finally covers reception, transport disposal, callback failure, abandoned enumeration and normal completion. Existing pending-result disposal and increment-before-yield behavior remain unchanged. In particular, a transport-disposal exception before the pending loop had no pending-result cleanup in baseline; this candidate clears the private scratch but does not fix or claim to fix that existing ownership limitation.

Tests cover mixed 16/2/3/17/2 logical sizes, callback failure at the first and second results, transport-disposal failure followed by another response, invalid alias followed by another response, overlapping enumerations, and scratch reuse while a caller still holds an earlier yielded result. Independent source and exact-exclusion reviews passed and are preserved in results/.
