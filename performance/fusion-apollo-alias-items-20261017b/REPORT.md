# C4: Temporary alias batch item storage

Status: prototype and 44 focused correctness tests complete. Actual-client BDN fixture compiled with zero warnings/errors, and three check-only oracles pass under default and fixed-four-heap policy. The prototype is ready for independent frozen benchmark preparation. No performance benefit has been measured. Baseline is `43a8dca2bd479ddc411d832ed97e42d9fcc8bd85`.

The warm TestQuery allocation trace attributes 584 allocation ticks and 62,248,544 sampled bytes (1.8019% of sampled bytes) to `AliasBatchItem[]` allocated by `HttpSourceSchemaClient.ExecuteAliasBatchAsync` under the Apollo batch node. Ticks are sampling observations, not calls or exact allocation. Actual plan/wire evidence has four alias transports containing ten items. The 64-byte item layout predicts 736 bytes/request across four array allocations; allocation measurement must verify that prediction. Alias-body CPU is only 149.637 sampled thread-ms, so no CPU speedup is claimed.

The prototype pools temporary item backing for at most 1024 entries. Both outer iterators return and clear their array in finally after collection, send, response splitting, yielded results and native fallback finish. No buffer is retained on the request store. Larger batches retain owned arrays. Pooling applies only to sealed `DefaultGraphQLHttpClient`; custom clients retain owned backing because they can keep the public request body. Default transport materializes byte content before callbacks, and the callback adapter exposes HTTP messages rather than the GraphQL request/body. Independent response-hotpath review followed that adapter and found no ownership blocker.

ArrayPool's minimum bucket capacity is 16. Four overlapping small buffers occupy 4192 bytes (four arrays of 16×64+24), compared with 736 exact bytes. Pool capacity and clearing may add CPU and memory cost. The 1024-entry cap is per buffer, not a global retained-memory bound; global retention remains runtime-managed.

This mechanism differs from C1 dedup scratch reuse, C2 error-attribution arrays, C3 duplicate paths and all 25 excluded authored experiments. In particular, it does not flatten the singleton iterator from PR 10578. Only one production source file changes; public signatures and immutable-array contracts stay intact.

Release correctness: 44 focused AliasBatch tests passed, no failures or skips. New cases cover overlapping result indices, cancellation followed by reuse, 1024/1025-item serialization and custom-client body retention. Existing cases include forwarding, errors, native fallback and abandoned enumeration. Initial compile errors and a zero-discovery test invocation are preserved beside the successful direct xUnit invocation/log/XML. The new standalone BDN fixture initially had a value-type initializer compile error; its failed log is also retained.

`Bdn/` exercises actual `HttpSourceSchemaClient` plus sealed `DefaultGraphQLHttpClient` and a controlled message handler. Cases are an ordinary native request, an alias batch of two requests and four sequential alias batches totaling ten items. It consumes complete result values/indices and includes serialization, response parsing/splitting, iterator disposal, pool clearing and request context/arena cleanup. Arenas seal before cleanup and dispose per operation. Schema/static payloads are prepared outside timing. The handler captures full wire requests only during check-only oracle setup; default transport still materializes the body during measured operations. This is a production-client microbenchmark, not the full original HTTP workload or concurrent overlap.

Default-GC genuine BenchmarkDotNet elapsed timing includes the user-required native MemoryDiagnoser allocation/GC columns. Process-scoped calibrated allocation remains a separate corroborating mode. Native MemoryDiagnoser uses its own forced-GC/extra-statistics phase; no NoGC region is installed in BDN setup. Its default-policy process counter values are reported as native measurements, with inconsistent or clamped values flagged rather than treated as zero allocation. The allocation mode requires fixed four-heap server GC with dynamic adaptation disabled, validates both process/thread known-allocation counters before and after each region, zero collections, successful NoGC termination and complete operations, and reports unsubtracted idle/background observations. It cannot establish default-policy total allocation. An intended fixed-policy check-only invocation accidentally entered allocation mode due a harness dispatch edit and stopped on a process-calibration mismatch. Its full source and logs are preserved under `results/invalid-verify-fixed-dispatch`; the unauthorized shared-lock attempt is excluded from evidence. The dispatch was corrected and independently reviewed before final check-only validation, which completed exactly one operation per case with no warmup or measurement. No accepted measurements have run. The benchmark owner will freeze exact baseline/candidate overlays and bounded launch settings; meaningful extra elapsed/CPU cost or inconclusive evidence stops the candidate without favorable-result retries.
