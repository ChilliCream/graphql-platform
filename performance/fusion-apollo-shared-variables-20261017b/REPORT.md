# C14: Allocate alias shared-variable lists only when needed

Status: **ABANDONED** after the bounded joint C14/C15 native BDN gate. The small observed allocation saving did not establish a worthwhile net tradeoff. All 41 focused correctness tests passed, including two forwarding-isolation cases; independent source and result reviews passed. The isolated prototype starts at `43a8dca2bd479ddc411d832ed97e42d9fcc8bd85`.

The existing warmed original-request profile attributes 117 allocation ticks and 12,469,240 weighted sampled bytes (0.36095%) to `List<Utf8VariableDefinitionNode>` under `HttpSourceSchemaClient.ExecuteAliasBatchAsync`. Sampling establishes recurrence, not exact call counts. The captured original request makes four alias HTTP requests. Their variables are only prefixed representation variables, with 2/3/2/3 items. Four empty list objects give a 128-byte per-original-request upper bound before any changed async-state size or other cost.

Both alias entry points now start with a nullable local list. Forwarded-variable collection creates that list only when needed. The final body receives a private empty singleton when no list was created. The singleton is never passed to collection or conflict-demotion mutation, and the body and variable writer only read it. Existing nonempty forwarding and name-conflict behavior remain unchanged. There is no buffer pool, additional network lifetime or request-owned retained capacity.

The two new cases exercise the single-request and multi-request entry points with independently initialized empty and forwarded requests, then another empty request. Complete variable JSON snapshots verify forwarding remains isolated. All 39 existing alias-batching cases also pass, including variable conflict, fallback, error routing and disposal coverage. The Release build has zero errors and two existing ASP.NET deprecation warnings. An initial test launch incorrectly disabled patch roll-forward while requesting runtime 10.0.0; its host error is retained. No tests ran in that launch. The corrected command explicitly used installed runtime 10.0.12 and passed all 41 tests.

The exact authored-experiment audit in `results/exclusion-review.txt` confirms this is distinct from #10575 and #10558 coerced-variable dictionary capacity, #10574 deferred-cost links, and #10524 native forwarded-variable serialization. C1 dedup scratch, C4 outbound items, C11 formatter reuse, C12 async send and C13/C15 incoming scratch are not included.

The first gate will reuse the exact existing C12 actual HTTP-client fixture with independently overlaid engines. Its genuinely asynchronous alias2 case reaches this list construction, while ordinary, asynchronous ordinary and custom-client cases provide unaffected controls. Native BenchmarkDotNet MemoryDiagnoser and default-GC elapsed measurements are required, with separately calibrated allocation only corroboration. Expected removal is one empty 32-byte list per alias2 operation, not a promise of exact whole-process savings. Meaningful added elapsed cost, negligible savings, or inconclusive evidence stops the candidate without a favorable rerun. No network throughput or process CPU claim follows from this fixture.
