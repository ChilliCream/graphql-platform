# RabbitMQ transport: connection state audit

This audit checks how the Mocha RabbitMQ transport (`src/Mocha/src/Mocha.Transport.RabbitMQ`) handles every connection, channel, consumer and lifecycle state of RabbitMQ.Client 7.x. It verifies the six recommendations in `RABBITMQ_CONNECTION_STATES.md`, compares Mocha with MassTransit, NServiceBus and Wolverine, and fixes the bugs it found.

## 1. State table

Fault injection uses only the existing `RabbitMQFixture` and `rabbitmqctl`:

- a consumer timeout: `consumer_timeout` and `channel_tick_interval` set through `rabbitmqctl eval`, because RabbitMQ 3.11 has no `consumer-timeout` policy (`set_policy` rejects the key);
- missed heartbeats: the broker's reader, writer and heartbeat processes for the vhost are suspended through `rabbitmqctl eval`;
- a blocked connection: `set_vm_memory_high_watermark 0`;
- a broker restart: `stop_app` and `start_app`;
- `close_connection`, `close_all_connections --global`, `delete_queue` and `clear_permissions`.

## 2. Findings, ranked by severity

### Finding 1 (critical): request/reply breaks for good after the consumer connection recovers

**What happens.** Mocha's reply endpoint consumes a temporary queue, which is non-durable and auto-delete (`M:Topology/RabbitMQRoutingStrategy.cs:144-155`, `M:Topology/RabbitMQQueue.cs:90-94`). Only the dispatcher's connection declares it, during topology provisioning. Three paths delete that queue, and nothing declares it again:

1. After any recovery of the consumer connection (broker restart, missed heartbeats, a forced close), the client recovers the reply consumer, and then `OnConnectionRecoveredAsync` closes that recovered channel to open a new one (`M:Connection/RabbitMQConsumerManager.cs:105-111`, `:383-426`). Closing removes the queue's last consumer, the broker deletes the queue, and the new `basic.consume` fails with 404. `main` does the same through `basic.cancel`.
2. If only the consumer connection drops, the queue is deleted with its last consumer. The client's recovery then fails on that consumer and retries the whole attempt forever (`C:Impl/AutorecoveringConnection.Recovery.cs:603-622`). Every consumer on the connection stays detached until the 30 s health monitor replaces the connection.
3. Stopping the transport cancels the reply consumer, which deletes the queue, so a later `StartAsync` fails with 404.

The same applies to any queue an operator deletes: the consumer re-attaches with `basic.consume` only and retries 404 forever.

**What users see.** Every `RequestAsync` times out after a broker restart or a network blip, and replies are dropped as unroutable. The log repeats "Failed to re-attach consumer for queue response-… 404 NOT_FOUND" with backoff. Mocha's own `MessageBusHealthCheck` (a request round trip, `src/Mocha/src/Mocha.Hosting/Health/MessageBusHealthCheck.cs:6-24`) fails until the process restarts.

**Tests.** `ConnectionStateTests.RequestAsync_Should_Succeed_When_BrokerClosesConsumerConnection`, `Bus_Should_ResumeWithoutLeaks_When_BrokerRestarts`, `Bus_Should_ResumeWithoutLeaks_When_HeartbeatsMissed`, `ConsumerStateTests.Consumer_Should_RedeclareQueueAndBindings_When_QueueDeletedByOperator`, `ConsumerLifecycleTests.StartAsync_Should_ConsumeOnce_When_TransportStoppedBefore`.

**Fix (A).** Every attach declares the endpoint's queue, the bindings that target it, and their source exchanges on the consumer's channel before `basic.consume`, each according to its `AutoProvision` setting (`M+:RabbitMQReceiveEndpoint.cs:77-100`, `M+:Connection/RabbitMQConsumerManager.cs:391-395`). MassTransit declares the endpoint topology on every channel use (`MT:Middleware/ConfigureRabbitMqTopologyFilter.cs:53-81`), and Wolverine declares again on every listener rebuild (`W:Internal/RabbitMqListener.cs:374-401`).

### Finding 2 (high): one stuck handler stalls every queue on the consumer connection

**What happens.** Mocha ran handlers inside the client's `HandleBasicDeliverAsync` (`M:Connection/RabbitMQConsumerManager.cs:590-611`). When a channel closes, the client's reader loop waits for that channel's consumer dispatcher to drain before it reads any further frame (`C:Impl/Channel.cs:784`, `C:ConsumerDispatching/ConsumerDispatcherChannelBase.cs:229-233`). This happens for a broker channel close (consumer timeout, an ack with a bad tag, a 404) and for Mocha's own close when it stops or replaces a channel. A handler that does not observe its token (a blocking call, a library without token support, a long retry loop) keeps the reader loop parked. A broker `connection.close` parks the old connection's reader loop the same way, but the client starts recovery on a new socket first, so that case does not stall consumers.

**What users see.** All endpoints served by the consumer connection stop receiving. `CreateChannelAsync` hangs, so nothing re-attaches. After 3 to 4 heartbeat intervals the client declares its own heartbeat missing and drops the connection, and every unacked message on every queue is redelivered. With the default 60 s heartbeat that is about 3 minutes of total consumer outage, triggered by one slow handler hitting the 30 min consumer timeout.

**Tests.** `ConsumerStateTests.Consumers_Should_KeepReceiving_When_ConsumerTimeoutClosesChannelOfStuckHandler` reproduces it: a real consumer timeout on one endpoint, after which a send to another endpoint must still arrive. `ConsumerStateTests.Consumer_Should_Reattach_When_ConnectionClosedWhileHandlerIgnoresCancellation` covers the `connection.close` case and passes before and after the fix.

**Fix (C).** Each channel consumer copies the delivery body into a pooled buffer, queues the delivery and returns, so the client's callback never waits for a handler. As many Mocha workers as the endpoint's `MaxConcurrency` run the handlers, and return the buffer when a handler finishes (`M+:Connection/RabbitMQConsumerManager.cs:622-775`). The client's dispatch concurrency is set to 1. Deliveries queued on a lost or stopping channel are left unsettled, so the broker requeues them. Recommendation 1 proposed this. MassTransit and NServiceBus keep handlers on the client's dispatcher (`MT:RabbitMqBasicConsumer.cs:93-139`, `NSB:Receiving/MessagePump.cs:339-481`); NServiceBus limits the blast radius with one connection per queue. Wolverine hands off to its own workers in its Buffered, Durable and NativeAck modes (`WC:Runtime/WorkerQueues/BufferedReceiver.cs:345-376`).

### Finding 3 (high): publishes are lost without an error

**What happens.** Dispatcher channels had no publisher confirms (`M:Connection/RabbitMQDispatcher.cs:47`), so `BasicPublishAsync` returned once the frame was queued (`C:Impl/SessionBase.cs:136-148`). Any broker-side failure was invisible:

- a `basic.nack`, for example from a queue with `x-overflow: reject-publish`;
- a 404 on a deleted exchange, which closes the channel;
- a publish written while the connection was blocked or already dead but not yet detected.

The endpoint also returned the channel to the pool in a `finally` (`M:RabbitMQDispatchEndpoint.cs:35-43`), so the next, unrelated publish could reuse a channel whose close was still in flight, and that message was dropped too.

**What users see.** `SendAsync` and `PublishAsync` succeed and the message never arrives. The test showed a 404 publish to one exchange followed by a lost send to a healthy queue.

**Tests.** `PublishStateTests.SendAsync_Should_Throw_When_BrokerRejectsMessage`, `PublishStateTests.SendAsync_Should_Deliver_When_PreviousPublishMadeBrokerCloseChannel`, `PublishStateTests.PublishAsync_Should_NotReportSuccess_When_ConnectionBlocked`.

**Fix (D).** Dispatcher channels enable confirms with tracking and no confirm rate limiter, as NServiceBus does (`M+:Connection/RabbitMQDispatcher.cs:19-22,53`; `NSB:Connection/ConfirmsAwareChannel.cs:21-23`). Every publish now waits for the broker's confirm and throws `PublishException`, `AlreadyClosedException` or `OperationCanceledException`. A channel used by a failed operation is disposed in the background instead of pooled (`M+:RabbitMQDispatchEndpoint.cs:41-47`, `M+:Connection/RabbitMQDispatcher.cs:99`). Disposal does not hold up the caller, because closing a channel waits for the broker, which reads nothing from a blocked connection; an earlier version of this fix closed the channel inline, and a publish cancelled after 2 s returned only after the 20 s continuation timeout. MassTransit also enables confirms by default (`MT:Configuration/ConfigurationHostSettings.cs:28`).

### Finding 4 (medium): stopping an endpoint hangs on a handler that ignores cancellation

**What happens.** `RabbitMQReceiveEndpoint.OnStopAsync` disposed the consumer without the stop token (`M:RabbitMQReceiveEndpoint.cs:105`). `Channel.CloseAsync` without a token waits for running handlers indefinitely (`C:Impl/Channel.cs:214-270`). Probe: `CloseAsync` was still pending after 5 s and completed only when the handler returned.

**What users see.** Host shutdown hangs until the orchestrator kills the process. While the close is pending, the stall from finding 2 also blocks every other endpoint on the connection.

**Test.** `ConsumerLifecycleTests.StopAsync_Should_Complete_When_HandlerIgnoresCancellation` (stop with a 2 s token must complete and leave the message requeued).

**Fix (C).** `RegisteredConsumer.StopAsync(cancellationToken)` sends `basic.cancel`, cancels handlers, waits for them only until the stop token is cancelled, then closes the channel. That close is quick because the client's dispatcher no longer runs handlers (`M+:Connection/RabbitMQConsumerManager.cs:427-474,593-616`). The endpoint passes its stop token (`M+:RabbitMQReceiveEndpoint.cs:131`). `DisposeAsync` does not wait for handlers. MassTransit bounds its drain the same way (`MTC:Transports/ConsumerAgent.cs:160-204`).

### Finding 5 (medium): connection-loss cleanup blocks the client's reader loop

**What happens.** The connection-shutdown handler awaited `OnConnectionLostAsync` inline (`M:Connection/RabbitMQConnectionManagerBase.cs:224-235`). For the dispatcher that closed every pooled channel (`M:Connection/RabbitMQDispatcher.cs:95-98,116-131`). The client raises the event on its reader loop or heartbeat timer (`C:Impl/Connection.cs:435-452`; `C:Impl/Connection.Heartbeat.cs:112-129`), which is the only code that could read the `close-ok` the close waits for. A dump taken during a slow dispose showed `RabbitMQDispatcher.ClearChannelPoolAsync` → `AutorecoveringChannel.CloseAsync` waiting under `Connection.ClosedViaPeerAsync` on the receive loop. When the close finally failed, `DisposeChannelSafelyAsync` skipped `DisposeAsync`, so the channel stayed recorded and the client's recovery resurrected it with no owner.

**What users see.** Disposing the bus during an outage took about 15 s. After a broker restart the dispatcher connection kept one extra channel forever. After missed heartbeats the old connection stayed open on the broker for about 20 s.

**Tests.** `ConnectionStateTests.DisposeAsync_Should_LeaveNoConnection_When_BrokerUnreachableDuringRecovery`, `Bus_Should_ResumeWithoutLeaks_When_BrokerRestarts`, `Bus_Should_ResumeWithoutLeaks_When_HeartbeatsMissed` (these compare connections, consumers and consumer channels with those before the fault, and allow at most two idle publish channels).

**Fix (E).** Loss handling runs on the thread pool (`M+:Connection/RabbitMQConnectionManagerBase.cs:350-394`), and a pooled channel is always disposed, even when closing it fails (`M+:Connection/RabbitMQDispatcher.cs:127-151`).

### Finding 6 (medium): two recovery mechanisms compete

**What happens.** The client's automatic recovery restored channels and consumers, then Mocha closed them and opened new ones (`M:Connection/RabbitMQConsumerManager.cs:105-111`). Meanwhile the 30 s health monitor could dispose a recovering connection and run its own five attempts (`:149-189`). Consequences:

- the deterministic deletion of the auto-delete reply queue (finding 1);
- deliveries to client-recovered consumers in the window before Mocha's replacement were neither handled nor settled until that channel closed, so they came back as redeliveries;
- consumer re-attach ran inside the client's `RecoverySucceededAsync` handler, where a further connection drop loses recovery (`C:Impl/AutorecoveringConnection.Recovery.cs:51-58,120-124,255`);
- outages longer than 30 s added up to about 45 s of extra downtime;
- recovery failures caused by topology are only written to the client's EventSource, so Mocha's logs did not show them.

**Tests.** The connection tests above. Each snapshot checks that recovery leaves no extra connections, consumers or consumer channels, and at most two idle publish channels.

**Fix (B).** Mocha is the only owner of recovery. On a shutdown not initiated by the application it disposes the lost connection, which cancels the client's recovery loop in 7.2 (`C:Impl/AutorecoveringConnection.cs:315-327`). The consumer manager then reconnects with 1 to 10 s backoff and re-attaches every consumer; the dispatcher reconnects on its next publish (`M+:Connection/RabbitMQConnectionManagerBase.cs:191-255,350-394`). This works whatever the application's factory sets for `AutomaticRecoveryEnabled`, so Mocha does not need to change that shared object. NServiceBus relies on the same dispose behavior (`NSB:Receiving/MessagePump.cs:297-336`). MassTransit turns client recovery off in a factory it builds itself (`MT:RabbitMqAddressExtensions.cs:42-44`).

### Finding 7 (medium): the transport does not start without a broker

**What happens.** `OnBeforeStartAsync` awaited both connections with five attempts and then threw (`M:RabbitMQMessagingTransport.cs:328-331`; `M:Connection/RabbitMQConnectionManagerBase.cs:137-192`). The consumer manager's health monitor starts only after a first connection (`M:Connection/RabbitMQConsumerManager.cs:83-92`).

**What users see.** A broker that is briefly unavailable during a deploy makes the host fail to start after about 15 s.

**Test.** `ConnectionStateTests.StartAsync_Should_Complete_When_BrokerUnreachable`.

**Fix (F).** One attempt per connection. A connectivity failure logs a warning and starts the background reconnect; refused credentials, refused vhost access and broker rejections (403, 404, 405, 406, 530) still fail the start (`M+:Connection/RabbitMQConnectionManagerBase.cs:112-158`). MassTransit behaves the same way (`MTC:MassTransitBus.cs:182-247`; `MT:Configuration/RabbitMqHostConfiguration.cs:47`). `StartAsync_Should_FailFast_When_VirtualHostAccessRefused` pins the fail-fast part.

### Finding 8 (low): a consumer whose first attach fails is attached later anyway

**What happens.** `RegisterConsumerAsync` added the registration before attaching and left it in place when the attach threw (`M:Connection/RabbitMQConsumerManager.cs:57-62`). The endpoint start fails, but the next reconnect attaches the registration.

**What users see.** After a failed start that the application survives, messages are consumed by an endpoint that is not started.

**Test.** `RabbitMQConsumerManagerRecoveryTests.RegisterConsumerAsync_Should_LeaveNoConsumerBehind_When_FirstAttachFails`.

**Fix.** A registration the broker refused is disposed before the exception propagates. A registration that failed only because the connection was lost is kept, because the new connection attaches it (`M+:Connection/RabbitMQConsumerManager.cs:88-107`).

### Finding 9 (low, tests): the existing connection-recovery tests never dropped a connection

**What happens.** `RabbitMQFixture.CloseAllConnectionsAsync` ran `rabbitmqctl close_all_connections <reason>` (`src/Mocha/test/Mocha.Transport.RabbitMQ.Tests/Helpers/RabbitMQFixture.cs:44` at `aee642f8b5`). Without `-p` or `--global` that command only closes connections to vhost `/`, and every test uses its own vhost. Probe: "Closed 0 connections".

**What users see.** `ConnectionRecoveryTests` passed without exercising recovery.

**Fix.** The fixture passes `--global`. The three existing tests pass with the fixes.

## 4. Public API and behavior changes

### Public API

- **Removed:** `protected virtual Task RabbitMQConnectionManagerBase.OnConnectionRecoveredAsync(CancellationToken)`. Mocha no longer uses the client's recovery, so the hook never fired. Subclasses outside the repo that override it no longer compile.
- **Added:** `protected void RabbitMQConnectionManagerBase.StartReconnecting()`.
- **Changed contract:** `RabbitMQConsumerManager.RegisterConsumerAsync` no longer leaves a registration behind when the broker refuses the first attach. It no longer throws when the connection is lost during the first attach; the registration is attached on reconnect.

Internal additions, not public: a `RegisterConsumerAsync` overload that takes a provisioning callback, `RegisteredConsumer.StopAsync`, `RabbitMQConnectionManagerBase.ConnectOrRetryInBackgroundAsync` and `RabbitMQDispatcher.DiscardChannel`.

### Behavior

- **Publisher confirms are always on.** Every send and publish waits for the broker's confirm, which adds one round trip of latency per message; concurrent publishers still use separate pooled channels. Rejected publishes, publishes to a missing exchange and publishes on a closing channel now throw `PublishException`, `AlreadyClosedException` or `OperationInterruptedException`. A publish during a blocked connection waits until it is unblocked or the caller's token is cancelled; after a cancellation the message may still be delivered.
- **Handlers run on Mocha's workers**, not on the client's consumer dispatcher. Each delivery's body is copied into an `ArrayPool<byte>` buffer, which is returned when the handler finishes. The body's lifetime is unchanged: it ends when the pipeline returns. `MaxConcurrency` applies per channel, so handlers abandoned on a lost channel can still be running next to handlers of the new channel, as before.
- **Endpoint stop** waits for running handlers until the stop token is cancelled, then abandons them; their deliveries are requeued by the broker. Previously it waited indefinitely for a handler that ignored cancellation.
- **Consumers declare their topology on every attach**: the queue, the bindings that target it and their source exchanges, each only when auto-provisioned. This adds a few RPCs at startup and on each re-attach.
- **Mocha owns recovery.** A connection lost to the broker or the network is disposed and replaced, whatever the factory's `AutomaticRecoveryEnabled` setting. Reconnect backoff is 1, 2, 4, 8, then 10 s. The dispatcher reconnects when the next publish needs a connection.
- **Startup** succeeds while the broker is unreachable, logs a warning and connects in the background. Refused credentials, refused vhost access and broker rejections of topology still fail the start, now at once instead of after five attempts.
- **Logs.** Removed: "Connection recovery succeeded", "Successfully recovered connection, topology, and consumers", "Error during post-recovery operations", "Connection recovery failed. Will retry". Added: "Could not connect to the broker. Connecting in the background, consumers attach once it is reachable" (Warning) and "Error while handling the loss of the connection" (Error). Changed: "Reconnection attempt {Attempt} failed. Retrying in {Delay}". Exceptions escaping a handler on a worker are logged as "Error processing message from queue {Queue}" instead of the client's callback-exception event.
- **Test fixture.** `RabbitMQFixture.CloseAllConnectionsAsync` now closes connections in every vhost.

## 6. Found but not fixed

- **`mandatory` is still off.** A send to a queue that was deleted after provisioning is dropped as unroutable without an error. NServiceBus sets `mandatory` for sends; MassTransit and Wolverine do not. Enabling it would make sends fail while a receiving service's queue is missing, which is a product decision.
- **Dispatch endpoints do not re-declare a deleted exchange.** Publishes now fail loudly, but keep failing until a restart. The existing test `RabbitMQDispatchProvisioningTests.PublishAsync_Should_NotReprovision_When_ResourceDeletedWhileConnectionStaysOpen` pins this as intended.
- **No per-consumer health check** (recommendation 6). It needs new public API, and the existing round-trip check covers request/reply.
- **Blocked connections do not fail fast.** Publishes wait on the confirm until the caller's token is cancelled, as in MassTransit and NServiceBus. A publish without a token waits until the broker unblocks.
- **Consumer timeout on RabbitMQ 4.3 and later** (sent as `basic.cancel`) is covered only through a deleted queue, which takes the same code path. The fixture runs RabbitMQ 3.11. A CI matrix over 3.12, 4.1 and 4.3 would cover the version-specific behavior end to end.
- **An abandoned handler keeps running.** Mocha cancels its token but cannot stop code that ignores it. Its delivery is redelivered, so the work can run twice; NServiceBus avoids a second run in the same process with an LRU of failed acks (`NSB:Receiving/MessagePump.cs:417-429`).
- **RPC timeouts on consumer channels.** A late reply after a timed-out `basic.qos` or `basic.consume` can complete a different RPC or leave a consumer the client does not know about (`C:Impl/RpcContinuationQueue.cs:146-168`; client report Q11). The re-attach then fails and retries, but this path is not tested.
- **Detection of a dead connection still takes 3 to 4 heartbeat intervals**, which is client behavior. Publishes in that window now fail instead of being lost, because they wait for confirms.
- **Recommendation 3's remaining claims** about a semaphore released by a cancelled confirmed publish and an intermittent `CloseAsync` deadlock were not verified.
