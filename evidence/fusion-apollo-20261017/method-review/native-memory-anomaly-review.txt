Pinned .NET10.0.12 installation identifies dotnet/dotnet commit95017c711e6afc1085133d440e42b4bd78155701. GCInterface_GetTotalAllocatedBytesPrecise suspends managed execution, reads GCHeap::GetTotalAllocatedBytes, subtracts unused dead-thread and live allocation contexts, then resumes. The GC heap implementation sums cumulative SOH/UOH counters only for indices below current n_heaps. Initial heap creation zeros those counters; the dynamic heap-count change path decommissions/recommissions existing heaps while changing n_heaps, and the reviewed decommission/recommission functions do not reset or transfer these total-allocation counters.

Source-based hypothesis: shrinking active heap count can remove previously accumulated per-heap contributions from the reported aggregate; later reactivation can add historical contributions. If such a transition occurs between the diagnostic boundary reads, a large apparent positive or negative delta is plausible without a corresponding volume of allocations in that interval. BenchmarkDotNet clamps a negative difference to zero. This explains a possible accounting mechanism, not the actual cause of any observed run. No per-diagnostic heap-count timeline or raw before/after runtime counters were captured, and earlier C2 heap-transition evidence is a different process. Actual extra framework/pool/background allocations remain an alternative. No correction, subtraction, new run or rescue of terminal C6/C8 is justified.
